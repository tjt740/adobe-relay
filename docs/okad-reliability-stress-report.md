# Okad / Sub2 联动压测与回归报告

日期：2026-10-11。两个仓库均为本地分支 `codex/okad-sub2-reliability`，未推送、未部署。

## 数据与隔离范围

19:55（北京时间）完成生产分页快照：Okad 外部账号 204 个，Sub2 Adobe 账号 204 个，脱敏邮箱关联全部匹配。快照中 Okad 登录状态均为 `ok`，Sub2 为 200 个 `active`、4 个鉴权异常。这是两个系统记录的状态，不代表重新验证了 204 个 Adobe 账号，也不能将“历史登录成功”当作“当前可调度”。

生产操作为正常管理员登录、10 次低频分页 GET（每页 50 条，分页间隔 1 秒）及健康检查。没有生产并发压测、服务重启、配置变更、账号导入删除、Adobe 登录、额度刷新或模型生成。未下载账号的 Cookie、Adobe Token 或密码；邮箱在内存中加盐散列，保留状态、额度、关联 ID 等测试字段。快照保存在忽略目录、文件权限为 600，不进入代码提交。

未读取生产号池列表：代码检查发现其 GET 可能补建管理员镜像行。号池测试使用合成数据。没有获取服务器数据库完整备份或 CPU、内存指标；分页快照也不是事务一致性备份。测试前后生产 `/health` 均返回 200，结束时单次约 382 ms；这仅证明健康接口可达，不能单凭它证明所有业务请求正常。

本地用独立 SQLite 文件、PostgreSQL 临时 schema 和模拟上游运行测试。压力服务禁止连接非回环地址。扩容样本为 204 个外部账号复制 10 倍（2,040 条）加 40 个合成号池账号，Cookie 用假数据替代。该规模是测试数据规模，不是线上实际账号数量。

## 本轮发现与修复

| 问题 | 触发场景与影响 | 修复及验证 |
| --- | --- | --- |
| 并发同步首次建记录冲突 | 24 个请求同步同一来源，凭据和发送任务出现唯一键冲突 | 持有来源行的数据库写锁后读取 Cookie，序列化建记录和版本更新；24 并发只产生一个版本、一个发送任务 |
| 排队任务重复登录 | 同账号 24 个恢复任务由 3 个工作线程消费，旧逻辑只合并同时运行的请求，模拟登录执行了 20 次 | 按任务提交时间复用同来源已完成结果；修复后模拟登录仅执行 1 次，24 个任务都完成 |
| 联动列表查询随总数膨胀 | 2,040 个外部账号时，首页先读取全表并逐条查询状态，共 10,364 条 SQL | 数据库分页、限制加载字段、批量取状态；首页降至 8 条 SQL；另测外部账号与号池跨页边界、去重和空页 |
| 查看恢复能力会写数据库 | 号池缺少取信资料时，查询能力会将回退资料写回并提交 | 增加只读解析模式，查看列表与能力不回写；保留原登录流程需要的回填行为 |
| 首页统计漏掉较早账号 | 状态计数只基于最近一批发送记录 | 独立 SQL 聚合全部状态，明细取最近 100 条；650 条记录计数仍为 650 |
| 号池原有规则回归 | 开启可靠联动后，对已存在于 Sub2 的账号仍登录，且新入库遗漏 4,000 积分门槛 | 恢复先查库存、已有账号跳过和原积分门槛；失败保留 Cookie；回归测试覆盖两项 |
| 再验证失败后调度状态不正确 | 已启用账号再次确认鉴权失效、身份不符、额度或权益不足，可能仍可调度；鉴权失败后的中间超时也可能阻止后续恢复 | 确定性失败重新隔离；鉴权/身份失败清理缓存 Token；暂时网络失败不停止原本健康账号；保留恢复归属，人工暂停始终优先 |

手动验证码测试还发现测试环境自身的并发事务问题：旧 `StaticPool` 将 HTTP 与登录线程放在同一条 SQLite 连接，请求结束时可能回滚工作线程的写入。该测试改为与实际应用一致的文件数据库、独立连接，保留所有 Cookie 落库断言，完整回归通过。此项不作为线上业务缺陷计数。

## 2026-10-12：基础流程专项复查

本轮针对 Cookie 获取、IP 配置、状态展示、任务卡在登录中、Sub2 同步逐项复查。沿用上一轮的生产脱敏快照，在独立本地库回放；本轮没有请求生产服务、登录真实 Adobe 账号或消耗线上额度，也没有推送、部署代码。

### 复现并修复的兼容问题

| 用户关心的流程 | 复现的问题及修复 | 验证依据 |
| --- | --- | --- |
| Sub2 获取 Cookie | Okad 已有新 Cookie 时，手动验证码或缺少取信配置的账号会先被“不能自动登录”拦截。现在优先补推已有 Cookie，不要求重新登录。v2 拒绝回执补齐 email、job_id、state，避免 Sub2 误判身份不符 | 新 Cookie + 手动 OTP、新 Cookie + 缺少取信配置两种场景；旧同步回调在 v2 开关两侧仍返回 Cookie |
| 升级后继续同步 | 原有 pending 标记没有对应的持久发送任务，升级到 v2 后可能丢失补推。启动时补建发送任务，保留原 account_id；已存在的任务不重置 | v1 待推记录升级恢复；已有任务幂等；失败保留 Cookie |
| IP 与业务配置 | 自动分配开启但代理尚未分配时，验证可能走 DIRECT。现在等待代理；代理失效也等待。验证期间编辑同一个 IP 节点时，旧验证不能落库 | 本地 PostgreSQL 检查；代理未就绪时禁止创建上游客户端；同 ID 代理修改竞态检查 |
| 原账号配置保留 | 新入库遗漏原设置中的倍率，现已带入。Cookie 更新保留主代理、备用代理、分组、名称、并发、优先级、倍率和模型映射 | 真实 SQL 更新后逐字段检查；首次创建参数检查（倍率 2.5、并发 7、分组 3/4） |
| 库存与驾驶舱 | 新联动已经配置专用密钥，但库存和驾驶舱仍依赖旧管理员令牌，可能误报不可用。现在按当前 v2 目标和专用密钥读取无凭据库存；“在线”只计启用且可调度的账号，库存去重仍含暂停/错误账号 | 无管理员令牌的库存/驾驶舱用例；启用、暂停、错误三态计数；浏览器显示 3 条合成库存、2 个在线 |
| 同步状态与时间 | 旧页面状态没有同步回填，号池推送时间缺失；部分回执可能被过早显示为已同步。现在区分待验证、需处理和已完成，确认 Cookie 已接收才更新推送时间 | 原外部账号标记、号池时间、503 后恢复及请求字段检查 |
| 远端暂停/恢复/删除 | 发送任务完成后一直展示旧回执。现在约每 30 秒通过只读库存核对，反映远端暂停、恢复、删除；迟到的库存结果不能覆盖新的待发送版本 | 暂停→恢复→删除；旧库存与新 Cookie 版本竞态；浏览器区分 2 个可调度和 1 个保持暂停 |
| 一直显示登录中 | 任务异常结束后明细残留 running；服务重启漏处理 pool_login；停用联动后过期恢复任务也不收尾。现在补齐后端终态处理，并兼容旧页面里的历史残留记录 | 崩溃任务、过期租约、停用联动后的遗留任务；浏览器中历史 running 明细显示“本轮失败”，重登按钮可用 |

- Sub2 前端：原账号状态、创建、编辑、批量编辑 **215 项通过**；`vue-tsc --noEmit` 通过。服务端构建通过。
- 独立回环 HTTP 替身检查：完整执行恢复任务→获得新 Cookie→Sub2 验证 503→补推成功，登录仅执行一次。此项使用模拟 Sub2 HTTP 服务；实际 Sub2 的写库、验证和竞态由 Go/PostgreSQL 测试分别覆盖，不能宣称已经完成真实 Adobe 端到端验收。
