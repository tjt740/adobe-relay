# Adobe 突发请求内存预留修复（二期）

本次目标是减少短时间大量请求被本地内存预留拒绝，保留即时拒绝、防 OOM 和原业务功能。发布目标仅为主服务器 `173.234.15.150` / `https://creative.cheap`。分组 2、7 按用户确认继续暂停。

## 修复范围

一期将容器调为 12 GiB、Go 目标调为 9 GiB，并缩短上传解析阶段的预留，但原格式图片仍在慢速上游等待期间预留每张 32 MiB 输出空间，历史突发回放仍出现过多拒绝。

本次把输入解析、等待、输出处理分开计量。原格式原生 Adobe OpenAI 图片路径在付费提交前为每张图片预留 160 MiB 物理磁盘；下载及必要的 Base64 JSON 直接写入这份有上限的缓冲，使用只读文件映射供原有响应和对象存储接口读取。等待期间保留实际输入及每张 4 MiB 工作预算。文件创建后立即解除目录链接，处理结束或进程退出后释放，不遗留图片文件。

磁盘须保留 8 GiB 余量，Linux tmpfs/ramfs 不使用此路径。磁盘不可用时仍走原内存保护流程；转码、Gemini 和中转账号仍在提交前取得原输出预算。新路径不会为内存容量排队，不修改账号/用户并发配置。容器保持 12 GiB，`GOMEMLIMIT=9216MiB`，没有新增配置项或数据库迁移。图片预留池采用 Go 目标的 3/4（6.75 GiB），为其他 Go 工作保留 2.25 GiB，并继续在实际 Go 内存接近目标的 90% 时拒绝增长；容器另有 3 GiB 余量。

同一图片下载失败后的原 URL、原任务和出口切换逻辑保持，不因缓冲修改而重新生成。对象存储、URL / Base64 返回、计费、客户端断开后完成处理、告警和联动保持。

## 验证与限制

使用 2026-10-15 下午 3,075 条脱敏请求尺寸和时长记录。该记录包含客户重试，尺寸来自规范化审计 JSON，并非原始线长；307 条缺少时长的记录使用 180 秒。回放保留尺寸长尾、10% 未知 Content-Length 及真实解析/审计流程，输出使用已知大小的合成字节，不请求 Adobe 或数据库。

Linux 独立 CI 使用 4 CPU、12 GiB 硬上限、9 GiB Go 目标，禁网运行突发与按时序回放，并读取 cgroup 峰值和 OOM 事件。大图片场景额外收紧硬内存上限。400 路场景按已知合成输出尺寸预留磁盘，以适应 CI 磁盘容量；另设 64 路场景使用正式每张 160 MiB 的完整磁盘预留。不能把紧凑合成预留当成线上真实磁盘占用。

下午成功记录约 82.5% 未指定转码；混合场景以 17.5% 使用原内存输出预算和 Base64/JSON 编码，验证两种路径同时运行。合成数据不模拟真实图像解码，也不证明 Adobe 上游或出口可以稳定承载相同并发。

本地 macOS 全量物理预留、0.2 倍时序的初步结果为 2,739 / 3,075 接收、336 拒绝；该结果未被当作上线通过依据。6 GiB 预留池的混合回放接收 3,012 / 3,075，拒绝 63 条，拒绝时实际 Go 内存约 3.3 GiB；据此将池调整为 6.75 GiB 后复测。最终以 Linux 结果、兼容性检查和发布后只读审计为准。
