# Adobe 图片并发内存修复（2026-10-15）

仅发布主服务器 `173.234.15.150` / `https://creative.cheap`。用户明确选择：Sub2 从 2 GiB 扩至 8 GiB，不新增内存等待队列，容量不足立即返回 429。原业务并发、账号、代理、SMTP、告警、Okad 和下载重试同一张图片的行为保留。

## 原因与线上证据

原容器硬上限 2 GiB、GOMEMLIMIT 1536 MiB，宿主机约 16 GiB。内核确认多次 cgroup OOM，不能把所有 502 都归为 OOM，也不能仅凭退出 137 判断原因。

诊断应用 `c811477d654651142d15a3721e6c2a45ab6506ed`（PR #59、工作流 38701362305）加入仅本机 SIGUSR1 内存分配采样，不开放 HTTP 诊断接口。16:12:00 的样本在 GC 后仍占约 1559 MiB，原始请求缓冲与 multipart 图片副本合计约占存活堆 93%。原流程先读取、解析和审核整份图片，再等待原业务并发槽，导致很多暂时不能处理的请求已经持有大图。

诊断时曾通过 `docker kill --signal=USR1` 采样，随后 OOM 未自动拉起；16:06:39 已手动恢复同一容器。后续只使用宿主机 `os.kill(pid, SIGUSR1)`，不再通过 Docker kill 发信号。诊断审计目录 `/opt/adobe-relay/releases/adobe-memory-diagnostics-20261015/`，不包含图片或凭据正文。

## 修改

- 鉴权后、模型白名单读取请求体之前，图片请求先尝试预留内存预算。满载立即 429 / Retry-After: 1，不读取整份上传、不生成、不新增等待队列。取消、错误、正常返回都释放；已经接单且脱离客户端继续运行的任务仍保留容量直到结束。
- 预算为已配置有限 Go 内存目标的三分之一，按 32 MiB + 6 倍请求体预估并封顶；未知长度或压缩体预留整个预算。Go 已用内存达到目标 90% 时同样快速拒绝，为共享响应处理和其他接口留余量。该估算与 GC 软目标不是对任意负载绝不 OOM 的保证。
- multipart 仍使用标准解析器验证、处理 transfer encoding；内容与原请求相同的上传和遮罩复用不可变字节，避免在轮询/下载期间长期保留两份图片。解码后不同的内容保留独立缓冲；原请求、未知字段、转发、审核与计费保持。
- 仅修改持久 `resources.yml` 的 app.mem_limit：2g → 8g，app.environment.GOMEMLIMIT：1536MiB → 6144MiB。前后完整 Compose 解析结果必须只有这两处差异。硬限制不是立即分配；主机目前无 swap，扩容减少其他服务可用余量。

带 race 的中间件、真实路由、Adobe/Images/审核/异步任务回归；覆盖拒绝前不读 body、断线后容量保留、取消、未知/压缩长度、根路径共享预算、原模型策略、32 路大上传、图片/遮罩一致和 transfer encoding。独立 cgroup 压力脚本 `image-memory-stress.sh` 使用 48 个 40 MiB 合成上传，对比无保护的 2 GiB 与保护后的 2/8 GiB；不联网、不访问生产应用、账号或数据库。
